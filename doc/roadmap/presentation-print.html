The brief

A multi-campus boarding school, offline students

The school

  • Every student has a computer, with no internet access
  • Each campus has an IT department and its own server
  • Wants the app installed on each campus server
  • Wants to test it for one term (3 months)

The platform must

  • Track student work and let teachers set tasks
  • Give principals and directors visibility
  • Let a school admin invite, approve, and disable users
  • License, limit, deploy, and disable campuses remotely
  • Protect code, content, and the database on client servers
  • Keep a public online version with sign-in

Architecture

Two products, one owner console

Public cloud

Online app and control service

The public study app for anyone with internet, with its own accounts. Also hosts the control service the Plysoft Tech Team uses to license, deploy, and monitor every campus.

Campus appliance

Signed package on each campus server

Students and staff use it over the campus local network. It holds that campus's accounts, tasks, submissions, and learning records.

Student devices never need the internet. Each campus server needs one narrow outbound HTTPS connection to the control service. Without it, remote licensing, releases, and suspension cannot be guaranteed.

Architecture

The campus agent: the only process that calls out

  • Enrolls the server with a one-time token and a machine fingerprint
  • Pulls signed releases early and installs them only inside the campus maintenance window
  • Renews the license and keys on every heartbeat
  • Reports version, health, and approved seat count
  • Uploads campus summaries for directors
  • Forwards activity events from the outbox in near real time, and holds them while offline
  • Locks the campus app when the license is suspended or expired after the grace period
The agent pulls from the control service. Nothing is pushed into the campus network, so it works through school firewalls.

License and deployment lifecycle

Architecture

Licensing, trials, and remote control

Three-month trial

A signed trial license ending three months after start. Read-only during the grace period so teachers can export, then locked until extended.

Seat cap

Counts approved users. The server rejects approvals past the cap. The agent reports the count, and an edited license fails its signature.

Enrollment

One-time token, machine fingerprint, license bound to that server. A copied install never receives a key.

Releases

Signed images queued per campus. The agent verifies, backs up, swaps, and reports installed or rolls back.

Remote suspension

Key renewal stops. The app locks after the grace period, so blocking the connection only delays it briefly.

No outbound access

Fallback: IT carries a signed license file with a hard expiry. Suspension waits until it expires.

Architecture

Data flow rules

  • Student and staff browsers talk only to the campus app.
  • The agent pulls from the control service. The control service never pushes into the campus.
  • The campus server is the source of truth for learner records.
  • Activity events stream to the central activity database within seconds. User identities are replaced with campus-specific codes by default; each school's data agreement sets the detail level.
  • Aggregated summaries (completion by class, usage by subject, active seats) also leave the campus for directors.
  • Public and campus accounts never mix.
  • The labs gain a small reporting hook for lessons opened, simulations used, and time spent. The original simulation logic stays intact.

Campus agent and updates

Scheduling: any interval, no one on site

Chosen per release

  • Which campuses: all, a pilot campus first, or a named list
  • When: a date and time, a weekly window, or the next school holiday
  • Release track: pilot or stable
  • Urgency: normal waits for the window; a security fix installs as soon as safe
Per-campus settingExample
Maintenance windowEvery Sunday, 01:00–04:00 campus time
Blackout datesExam weeks, the first week of term
PostponingThe school admin can postpone once, for up to 7 days
Security overrideCritical fixes skip the window but never install during class hours
Daily, weekly, monthly, or one-off: changing the window changes the interval. The download happens ahead of time, so a slow school connection doesn't eat into the install window.

Campus agent and updates

Building the agent: two options

Option 1 · Recommended

Go

  • One self-contained program, no runtime to install
  • Builds for Linux and Windows from one codebase
  • Mature libraries: TLS, TPM (go-tpm), TUF (go-tuf), container control
  • Used by the AWS SSM Agent, Tailscale, Docker, and Kubernetes
  • Compiled code is harder for campus IT to read or modify
  • Cost: a second language alongside TypeScript
Option 2

TypeScript on Node.js

  • Same language as the app and control service; code can be shared
  • Packaged as one program with Node single executable applications or Bun
  • Fastest start for the current team
  • Costs: larger file with a bundled runtime, source easier to extract, weaker TPM libraries
  • Suitable for the one-term pilot if speed matters most, rewritten in Go before more campuses
Either way, licensing, key release, and the activity outbox are specific to this product and must be built. The choice is only how the agent itself is written.

// due reports whether a release may install now,
// with now given in the campus time zone.
func (j ReleaseJob) due(now time.Time) bool {
    if now.Before(j.NotBefore) {
        return false
    }
    today := now.Format("2006-01-02")
    for _, d := range j.Blackout {
        if d == today {
            return false
        }
    }
    if j.Urgent {
        return true
    }
    hm := now.Format("15:04")
    for _, w := range j.Windows {
        if now.Weekday() == w.Weekday &&
            hm >= w.Start && hm < w.End {
            return true
        }
    }
    return false
}

Real-time activity

Live activity from every campus, within seconds

Real-time activity

How it works

  1. Record on campus. The campus app writes each change and its outbox event in the same database transaction, so an event is never lost or recorded without its change.
  2. Forward. The agent sends new outbox rows in small batches as they appear, over a WebSocket or repeated HTTPS calls.
  3. Survive outages. Events wait in the outbox while offline. Unique event ids mean a resend never creates a duplicate.
  4. Store centrally. The ingest API checks the campus and its license, then writes to the central activity database.
  5. Show live. Dashboards update through server-sent events or WebSockets.

Rows are marked sent only after the ingest API acknowledges them, and pruned after a retention period.

Real-time activity

What the live dashboards show

  • Users signed in right now, per campus
  • Accounts invited, approved, and disabled
  • Tasks created and submissions handed in, as they happen
  • Lessons opened and simulations used, by subject and topic
  • Per campus: last event received and unsent backlog

"Real time" means seconds

When a campus is offline, the dashboard shows its lag and the time of its last event instead of presenting old figures as current.

Bandwidth

Events are small compressed JSON batches. On a slow link the agent sends live counts first and detailed events behind them.

Real-time activity

How much student detail leaves the campus

Live counts only

Numbers per campus, class, and subject, updated every few seconds.

Keeps all student records on campus. No central drill-down to one student.

Proposed default

Pseudonymous events

Each event, with user ids replaced by campus-specific codes.

Detailed trends without names. Only the campus server can match a code to a person.

Full events

Each event with the user's identity.

Full visibility in one place. Needs consent, a retention policy, and rules on which Plysoft staff may see it.

The level is agreed with each school before the pilot. Codes use a secret held on the campus server, so students cannot be linked across campuses or identified by the cloud.

Real-time activity

Securing the activity stream

  • Events travel over HTTPS from the agent, signed with the campus deployment key.
  • The ingest API rejects events from suspended, expired, or unknown deployments.
  • The central activity database is encrypted at rest and separate from the public app's database.
  • Directors see only their own school.
  • Plysoft staff access to activity data is limited to named roles and logged.
  • A director opens a named student's history on the campus app, or the central view asks the campus to resolve the code while the viewer is authorized.

Roles and permissions

Scope rules

  • A school contains one or more campuses. Every campus user belongs to exactly one campus.
  • Principals see only their campus.
  • Directors see all campuses of their school: live activity at the agreed detail level (pseudonymous by default), and named records on the campus app.
  • Teachers see only students in classes they teach.
  • Students see only their own work.
  • The school admin manages users only on their campus.
  • Platform admins manage licenses and deployments. They do not read campus learner records.
Every check is enforced on the server. Hiding a button in the UI is not authorization.

Security

Threat model

An administrator on the campus server can copy disks and read memory. The goal: casual access fails, copies are useless, leaks are traceable, and the contract covers the rest.

ThreatControl
IT copies the install to another machineLicense and keys bound to the machine fingerprint. A copy never receives a key
IT opens the database fileDatabase and backups encrypted. Key never in config or backups
IT edits the license for more seats or timeSigned licenses. An edited license fails verification
Outbound connection blocked to avoid suspensionShort-lived keys. The app locks after the grace period
A tampered release is installedAgent verifies image signature and digest first
Leaked content or code appears elsewhereContent and database watermarked with the campus id
Students reach another student's dataServer-side role and scope checks on every request
Public users reach school dataSeparate accounts and databases. No shared sign-in
Forged or replayed activity eventsSigned with the deployment key, unique ids, unknown or suspended deployments rejected

Security

Keeping campus IT out of the database

  • Encrypt the campus database file and every backup.
  • The control service releases the database key only to a valid license on the bound fingerprint.
  • Hold the key in memory and the operating system key store for the grace period. Never in app config, environment files, or backups.
  • Campus IT gets an operator role: start, stop, disk space, encrypted backups. No database password, no query console.
  • Every restart, backup, and restore is logged and reported on the heartbeat.
Limit: an administrator who dumps the running process can still read the key. Cover that with the contract and the audit trail.

Security

Code, content, sign-in, and transport

Code and content

  • Signed image, not source
  • No source maps or dev tooling
  • Lesson bundles encrypted, opened with the short-lived content key
  • Per-campus watermark
  • Contract: no export, no key extraction, no reverse engineering, right to audit

Authentication

  • Campus: Argon2 or bcrypt, campus-bound sessions, lockout after failed attempts
  • Public: managed provider with email verification and reset
  • Console: second factor for every Plysoft Tech Team member

Transport

  • Agent to control service over HTTPS with a pinned certificate
  • Campus app serves HTTPS on the local network with a certificate issued at enrollment

Security

Privacy

  • The campus server is the source of truth for student records.
  • Live events reach the central activity database with campus-specific codes by default. Sending identities requires the school's written agreement.
  • Summaries sent to the cloud contain aggregates only.
  • Platform admins do not read campus learner records. Plysoft staff access to central activity data is limited to named roles and logged.
  • Retention and deletion terms are agreed with each school before the pilot, for both the campus and central databases.
